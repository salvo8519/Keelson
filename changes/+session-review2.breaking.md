Sessions and e-mail addresses after the second security review. Upgrade consequences: every user signs in again once, because refresh tokens issued before the upgrade carry no session id and are refused, and impersonation tokens issued before it are refused too. `PATCH /users/me` no longer changes the e-mail address and answers 422 for any field outside the profile (`email`, `password`, `role`, `is_active`), where it used to ignore them. The address changes through `POST /users/me/email`, which always answers 202 (also for an address already in use, which receives nothing) and is limited per client IP and per user (category `email_change`, 3 an hour), and requires the current password (`current_password`, 400 when missing or wrong) or, for an account without a password, a sign-in within the last 5 minutes (403 `recent_sign_in_required`), and `POST /auth/email/confirm` with the token of the link sent to the new address; the address in force is told of the request and of the change. Links sent by e-mail carry their token in the URL fragment (`/reset-password#token=...`, `/confirm-email#token=...`, `/auth/magic-link#token=...`), so it no longer reaches web server logs; the bundled reset and confirmation pages also read links in the earlier form and remove the token from the address bar. No page is bundled for sign-in links (`/auth/magic-link`): a project that offers them must build one that reads the fragment. `PATCH /users/me/password` is now limited per client IP and, with `POST /users/me/email`, by one per-user budget of password attempts (category `reauth`, 5 every 15 minutes); a session that guesses the password gets 429 on both routes. Account e-mails are sent after the response (FastAPI background tasks): code that calls `UserService` outside a request still sends them at once, and `UserService` takes the background tasks as an optional second argument. `GET /users/me` returns `has_password`. Reset and sign-in links sent before the upgrade, and links sent to an address the account no longer has, stop working. Code that implements the token store of `app/core/revoked_tokens.py` needs `set(..., only_if_absent=True)` returning whether it wrote, and `time()`. `DELETE /users/me` now requires the same proof as an address change (body `{"current_password": ...}`, 400 when missing or wrong; 403 `recent_sign_in_required` for an account without a password and a sign-in older than 5 minutes) and is limited by category `reauth`; clients that delete accounts must send the password. The routes that check the current password (`PATCH /users/me/password`, `POST /users/me/email`, `DELETE /users/me`) no longer count against the per-IP limit of the sign-in routes (`auth`): category `reauth` has its own per-IP limit, 20 every 15 minutes, besides 5 every 15 minutes per user. While the rate limiter cannot reach Redis, the routes of categories `auth` and `reauth` (sign-in, registration, reset and sign-in link requests, address confirmation, workload tokens, invalid refresh tokens, and the three routes above) answer 503 with the code `RATE_LIMIT_UNAVAILABLE` instead of being served without a limit; other categories are still served. Custom rate limit storages must raise `RateLimitStorageUnavailable` when they cannot count, instead of allowing the call. While Redis does not answer, `POST /auth/refresh`, `POST /auth/session/refresh`, the single sign-on callback and `POST /oauth/exchange` answer 503 with the code `SESSION_STORE_UNAVAILABLE` (they answered 500), and both sign-out routes answer 503 with `revocation_recorded` false (`POST /auth/session/logout` removes the cookies all the same) instead of 500: sessions are not renewed and sign-outs are not recorded until Redis answers, and access tokens work until they expire. Per-user limits are now checked before per-IP limits, so a call refused per user no longer counts against the address.
